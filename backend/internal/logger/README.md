# 后端日志约定

沿用 `log.level`、`log.encoding`、`log.dir` 配置。业务、异常和生命周期日志通过 Zap 输出到终端及可选的按日文件；HTTP 访问日志由 Gin 输出到终端，不重复写入 Zap。

## 排查请求

每次请求由独立的 `RequestID` 中间件生成 `request_id`，通过 `X-Request-ID` 响应头返回。统一 JSON 响应只包含 `code`、`message`、`data`；JSON 和下载等非 JSON 响应均通过响应头提供请求 ID。不接受客户端提供的请求 ID。

请求 ID 的上下文 Key、响应头名称及 `GetRequestID` 读取方法归属 `request` 包。`logger` 只读取，不生成 ID；读取不到时返回空字符串，不自行补发另一个 ID。`RequestID` 中间件不承担访问日志格式或路由字段处理。

访问日志保留 Gin 的时间、彩色状态码、耗时、客户端 IP 和请求方法等显示风格，末尾追加 `request_id`。路径使用路由模板，未匹配路径记为 `unmatched`，不记录原始 URL、查询参数、请求头和请求体。用该 ID 关联 Gin 请求日志与 Zap 业务、错误日志。

panic 由 Zap Recovery 记录堆栈，不输出可能携带业务数据的 panic 值；尚未开始响应时返回统一 JSON 错误，请求 ID 通过响应头返回。连接已断开或响应已经开始时不追加 JSON，避免破坏文件下载等响应。

业务日志使用 `operation` 表示具体动作，数值实体 ID 用于定位操作目标。`actor_id` 直接记录操作者学号，暂不进行哈希或加密处理。反馈提交日志不附提交者标识。

Handler 使用原生 Zap 的 `With(OperationFields(c, operation)...)` 建立局部 `log`，后续错误、成功和清理日志复用该变量。`OperationFields` 只构造请求和操作字段，不创建或包装 logger，也不自动读取操作者。管理端 Handler 显式从已认证上下文添加 `actor_id`；登录仅在认证成功后添加，反馈提交不添加。中间件无具体业务操作时使用 `With(RequestFields(c)...)`。文件关闭和临时文件清理属于当前操作，沿用其 `operation`，由日志消息区分具体阶段。

`managementError` 只复用管理端 CRUD 共同的错误到响应码映射，未知错误在其默认分支记录一次。登录、密码、客户端请假等业务有不同的错误含义，继续在对应 Handler 显式判断，不强行套用通用管理错误映射。

## 级别和记录位置

- `Info`：关键业务写入成功、登录结果、服务初始化阶段。普通查询成功不重复记录业务日志，请求完成仅由 Gin 记录。
- `Warn`：主操作完成后的文件清理失败、附件关闭失败或请求连接断开。
- `Error`：最终由 Handler 或中间件处理的未知系统错误、服务启动失败和 panic。参数无效、资源不存在、密码错误等预期业务拒绝不视为系统错误。

向上传递的错误只在最终处理处记录一次。Service 仅记录自行处理、未向上传递的清理失败；这类底层日志沿用注入的 logger，目前不附请求 ID。成功日志在 Service 完成持久化或事务提交后记录。

错误字段统一使用 `logger.Error(err)`；MySQL 驱动错误隐藏可能包含字段值的消息，只保留错误码和 SQLSTATE。GORM 默认 SQL 输出关闭，避免重复日志和 SQL 参数泄漏。不要输出完整 DTO、密码、Token、电话号码、请假原因或反馈正文。

日志初始化之前及刷盘失败时使用标准错误输出兜底。独立的数据库迁移命令保持原有日志方式。
